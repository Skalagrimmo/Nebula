## 1. Призначення документа

Цей документ фіксує початкову концепцію модульного ігрового рушія, у якому різні мови програмування застосовуються за призначенням, а не змішуються в одному нерозділеному коді.

Основна ідея — побудувати систему, де:

- **Kotlin** відповідає за Android-застосунок, взаємодію з користувачем і життєвий цикл платформи;
- **Rust** є основою ігрового ядра та визначає правила взаємодії між основними системами;
- **GLSL ES** описує шейдерні програми, які виконуються на графічному процесорі;
- **Python** обробляє дані й надає інструменти для підготовки, перевірки та генерації ігрового вмісту;
- **ARM64 Assembly** використовується для окремих низькорівневих або спеціально оптимізованих операцій, де це виправдано.

Це не вимога використовувати всі мови в кожному ігровому циклі. Навпаки, кожен компонент має працювати автономно й контактувати з іншими тільки через заздалегідь визначені інтерфейси.

Документ є відправною точкою для проєктування. Він не вважається остаточним технічним стандартом: деталі, які залежать від експериментів на реальному Android-пристрої, мають бути перевірені прототипами.

## 2. Бачення та цілі

### 2.1. Головна мета

Створити невеликий, контрольований і розширюваний рушій, який можна розробляти на ARM64-пристрої, поступово переносити з прототипу в повноцінний Android-застосунок і розвивати без потреби переписувати весь проєкт при заміні окремої підсистеми.

### 2.2. Архітектурні цілі

1. **Модульність.** Світ, правила, події, графіка, завантаження даних, керування та інтерфейс мають мати чіткі межі.
2. **Зрозумілі контракти.** Модулі не повинні залежати від внутрішнього устрою один одного. Взаємодія відбувається через публічні функції, типи даних, повідомлення або стабільний ABI.
3. **Поетапна реалізація.** Наявний асемблерний прототип не потрібно викидати. Його можна перевіряти, документувати й поступово переносити або залишати там, де це має сенс.
4. **Придатність до Android.** Архітектура має враховувати обмеження пам’яті, енергоспоживання, сенсорного керування, призупинення застосунку та відновлення графічного контексту.
5. **Передбачувана продуктивність.** Часті операції ігрового циклу виконуються нативним ядром. Повільніші інструменти обробки вмісту не повинні без потреби запускатися в кожному кадрі.
6. **Можливість тестування.** Правила гри й роботу з даними треба мати змогу тестувати без графічного інтерфейсу.
7. **Розширюваність.** Додавання нового типу об’єкта, правила, формату даних або графічного ефекту не має вимагати змін у всіх інших компонентах.
8. **Переносимість.** Ядро не повинно напряму залежати від Android там, де достатньо абстрактного інтерфейсу платформи.

### 2.3. Що не є метою першого етапу

- Побудова універсального рушія рівня великих комерційних рушіїв.
- Передчасне перенесення кожної функції в асемблер або оптимізація без вимірювань.
- Вбудовування повного інтерпретатора Python у мобільний застосунок до появи конкретної потреби.
- Передавання всіх даних між мовами у вигляді JSON під час кожного кадру.
- Створення складної системи плагінів, мережевої гри чи редактора рівнів до стабілізації базових модулів.

## 3. Основні архітектурні принципи

### 3.1. Одна відповідальність на компонент

Кожен модуль має одну провідну відповідальність. Наприклад, Kotlin обробляє життєвий цикл Android, але не визначає правила зіткнень або логіку станів ігрових об’єктів. Python перевіряє й готує дані, але не є основним джерелом істини для стану активного світу. GLSL ES виконує графічні програми на GPU, але не керує всією системою рендерингу.

### 3.2. Ядро володіє ігровим станом

Під час виконання гри **Rust є авторитетним власником стану світу**: об’єктів, правил, черги подій і системної логіки. Інші модулі відправляють ядру команди або отримують підготовлені результати. Це зменшує ризик того, що різні мови зберігатимуть суперечливі копії одного й того самого стану.

### 3.3. Дані не тотожні мові, що їх обробляє

Ігрові дані зберігаються у файлах визначеного формату. Python може створювати, перевіряти, мігрувати або компілювати ці файли, але самі дані не мають бути зашиті у Python-код лише тому, що Python обраний для їхньої обробки.

### 3.4. Межі мов мають бути явними

Не можна безпосередньо передавати довільні внутрішні типи Rust у Kotlin, C або Assembly. На межах використовуються стабільні контракти: JNI, C ABI, визначені структури, ідентифікатори ресурсів, дескриптори або формати файлів.

### 3.5. Оптимізація після вимірювань

ARM64 Assembly застосовується для конкретних функцій, для яких профілювання показало потребу в оптимізації або де низькорівневий контроль є частиною експерименту. Сам по собі асемблер не гарантує швидшого виконання: результат залежить від компілятора, процесора, алгоритму й характеру даних.

### 3.6. Мінімізувати кількість переходів через межі модулів

Переходи між мовами мають бути крупнозернистими. Наприклад, виклик одного нативного методу на кадр може передати ядру час кадру й зведений ввід, а не викликати JNI окремо для кожного об’єкта або кожної графічної команди.

## 4. Ролі мов і компонентів

## 4.1. Kotlin — Android-оболонка

**Основна роль:** інтеграція рушія з платформою Android.

Kotlin відповідає за:

- `Activity` або іншу верхньорівневу точку входу застосунку;
- екрани меню, налаштування та системні діалоги;
- сенсорне керування й перетворення торкань на узгоджений формат вводу;
- життєвий цикл застосунку: запуск, паузу, повернення з фону та завершення;
- створення графічної поверхні й координацію графічного потоку, якщо це буде обрано в Android-реалізації;
- виклики нативного API ядра через JNI;
- Android-специфічні можливості: системні налаштування, вібрацію, дозволи, аудіофокус та інші інтеграції, якщо вони знадобляться.

Kotlin **не повинен** дублювати систему правил гри, зберігати незалежну від Rust копію стану світу або виконувати важкі цикли симуляції.

### Межа Kotlin–Rust

Для початкової реалізації рекомендовано тонкий JNI-шар. Kotlin передає ядру зведені команди вводу та повідомлення життєвого циклу, а ядро повертає компактні результати: статус виконання, інформацію для інтерфейсу або інші дані, визначені API.

JNI — це транспортна межа, а не місце, де має жити ігрова логіка. Деталі пам’яті, ресурси Rust і складні внутрішні структури не слід відкривати напряму Kotlin-коду.

## 4.2. Rust — ядро рушія

**Основна роль:** авторитетна ігрова логіка та координація підсистем.

Запропонований склад ядра:

- **Engine Core:** ініціалізація, завершення й узгоджена послідовність роботи систем;
- **World:** об’єкти, типи, стани, зв’язки та правила життєвого циклу об’єктів;
- **Rules:** перевірка умов і застосування дій;
- **Events:** створення, черга, доставка й обробка подій;
- **Input:** перетворення команд платформи на внутрішні ігрові команди;
- **Data/Level Loader:** читання перевірених даних рівня й перетворення їх у внутрішнє представлення;
- **Resource Manager:** облік і життєвий цикл текстур, шейдерів, буферів та інших ресурсів;
- **Renderer Interface:** API, через який ігрова логіка надає рендереру дані для малювання;
- **Diagnostics:** журнали, помилки, лічильники й діагностичний стан;
- **Platform Abstraction:** мінімальний набір операцій, які ядро запитує від платформи, якщо вони не можуть бути реалізовані переносимим способом.

Розділення на внутрішні Rust-модулі можна почати з `mod` і окремих файлів в одному crate. Не обов’язково відразу робити кожний компонент окремим динамічним плагіном або окремою бібліотекою. Фізичне розділення варто вводити лише тоді, коли воно полегшує тестування, збірку або заміну компонентів.

## 4.3. OpenGL ES і GLSL ES — графічна підсистема

Важливо розрізняти дві частини:

- **Рендерер** — програмний компонент, який готує ресурси, створює графічні команди, керує станом OpenGL ES і викликає малювання. Його доцільно реалізовувати на Rust, використовуючи відповідні нативні OpenGL ES bindings.
- **Шейдери GLSL ES** — невеликі програми, які компілюються графічним драйвером і виконуються на GPU, наприклад vertex- і fragment-шейдери.

Рендерер відповідає за:

- створення та перевірку графічних ресурсів;
- завантаження, компіляцію й компонування шейдерів;
- завантаження текстур і геометрії;
- підготовку даних сцени;
- налаштування стану графічного конвеєра;
- передачу команд малювання в OpenGL ES;
- відновлення ресурсів після втрати графічного контексту;
- виведення діагностики помилок GPU.

Шейдери відповідають лише за ті частини графічних обчислень, для яких вони призначені: перетворення вершин, обчислення кольору, освітлення, семплювання текстур, ефекти матеріалів тощо.

### Початкове рішення щодо Android-графіки

Для першого Android-прототипу розглядається варіант, у якому Kotlin створює `GLSurfaceView`, а методи зворотного виклику його рендерера запускають нативну функцію Rust на потоці, де графічний контекст уже активний. Це може спростити початкову інтеграцію, але вимагає уважно обробляти створення та втрату контексту.

Альтернативою є власне керування EGL і графічною поверхнею в нативній частині. Остаточний вибір потрібно зробити невеликим технічним прототипом, а не припускати, що обидва варіанти взаємозамінні без додаткової роботи.

### Вимоги до рендерера

- Ігрова логіка не повинна викликати OpenGL безпосередньо з довільних місць ядра.
- Рендерер працює на потоці з поточним графічним контекстом.
- Життєвий цикл GPU-ресурсів відокремлений від життєвого циклу логічних об’єктів.
- Дані, потрібні для кадру, передаються як підготовлений знімок або інше чітко визначене представлення.
- Втрата контексту не повинна знищувати логічний стан світу; графічні ресурси потрібно створити повторно.
- Ключові графічні помилки мають бути доступні через журнал або діагностичний екран.

## 4.4. Python — дані та інструменти розробки

**Основна роль:** обробка ігрового вмісту до його використання ядром.

На першому етапі Python рекомендовано використовувати для:

- перевірки синтаксису файлів рівнів;
- перевірки посилань між об’єктами й коректності ідентифікаторів;
- перевірки допустимих типів, станів, дій та умов правил;
- перевірки обов’язкових полів і діапазонів значень;
- генерації тестових світів і великих наборів об’єктів;
- міграції даних між версіями формату;
- підготовки або конвертації ресурсів;
- створення діагностичних звітів;
- майбутніх допоміжних інструментів для редагування контенту.

### Де зберігати дані

Самі дані мають бути декларативними файлами, наприклад JSON, TOML або власним текстовим форматом. Для першого прототипу краще обрати один основний формат, щоб не підтримувати одночасно кілька рівнозначних способів опису тих самих сутностей.

Пропонований процес:

1. Розробник змінює файл рівня або конфігурацію.
2. Python-валідатор перевіряє структуру, типи, посилання та правила узгодженості.
3. За потреби інструмент конвертує вихідний файл у підготовлений або компактний формат.
4. Rust завантажує дані й робить повторну перевірку критичних умов безпеки та цілісності.
5. Після завантаження саме Rust володіє активним станом світу.

На Android Python не повинен бути обов’язковим компонентом runtime у першій версії. Це дозволить не пакувати інтерпретатор і не створювати додаткову складність, якщо всі потрібні дані можна завантажувати безпосередньо Rust-ядром.

### Можливе майбутнє розширення

Якщо з’явиться потреба в користувацьких сценаріях, модифікаціях або динамічній логіці під час гри, питання вбудовування Python можна переглянути окремо. Таке рішення матиме ціну: розмір застосунку, пакування залежностей, підтримка Android ABI, доступ до API, помилки виконання й обмеження безпеки.

## 4.5. ARM64 Assembly — спеціалізований низький рівень

**Основна роль:** вузькі функції, де потрібен прямий контроль над інструкціями процесора або збереження вже працюючого прототипу.

Асемблер можна використовувати для:

- експериментальних низькорівневих процедур;
- спеціалізованих операцій над компактними структурами даних;
- окремих циклів, продуктивність яких підтверджено вимірюваннями;
- SIMD-операцій, якщо задача й архітектура дають реальну перевагу;
- дослідження механіки ARM64 та роботи з ABI;
- поступового збереження частин наявного асемблерного прототипу, поки його поведінка коректна й перевірена.

### Чого не слід робити

Не варто використовувати асемблер як загальний маршрутизатор усіх повідомлень між модулями. Низькорівневий код важче підтримувати, розширювати, аналізувати й тестувати. Контракти між модулями мають бути визначені на архітектурному рівні, а диспетчеризацію й керування залежностями краще залишити Rust-ядру.

Асемблерна функція може бути викликана через визначений C ABI. Для кожної такої функції потрібно зафіксувати аргументи, результат, побічні ефекти, використані регістри, правила збереження регістрів, вирівнювання та поведінку при помилкових вхідних даних.

## 4.6. C — допоміжний міст, а не обов’язковий окремий рівень логіки

У прототипі вже є C-завантажувач рівнів. C може залишатися невеликим сумісним прошарком, коли він спрощує виклик наявного коду або інтеграцію з JNI/NDK. Водночас не потрібно додавати C як ще один повноцінний шар логіки без потреби.

Під час міграції слід перевірити, чи варто залишити завантажувач на C, перенести його у Rust або тимчасово зберегти як перевірену зовнішню функцію. Рішення має спиратися на зручність, коректність, тестування та обсяг необхідних змін.

## 5. Логічна схема компонентів

```text
Android / Kotlin
  ├─ меню та налаштування
  ├─ сенсорний ввід
  ├─ життєвий цикл застосунку
  └─ графічна поверхня / виклики JNI
             │
             ▼
     Тонкий нативний міст
             │
             ▼
         Rust Engine
  ├─ стан світу та об’єкти
  ├─ правила
  ├─ черга подій
  ├─ команди вводу
  ├─ завантаження даних
  ├─ ресурси та діагностика
  └─ інтерфейс рендерера
        │             │
        ▼             ▼
  ARM64 Assembly   Rust Renderer ─── OpenGL ES
  через C ABI                         │
                                      ▼
                                  GLSL ES / GPU

Python tooling ── перевіряє, готує та конвертує файли даних
       │
       ▼
Декларативні файли рівнів, об’єктів, правил і конфігурацій
```

Схема показує логічні залежності, а не обов’язково окремі процеси чи бібліотеки. На першому етапі кілька компонентів можуть збиратися разом, доки їхні межі залишаються чіткими.

## 6. Взаємодія між модулями

### 6.1. Правило залежностей

Рекомендований напрям залежностей:

- Kotlin залежить від публічного нативного API, а не від внутрішніх структур світу.
- Ігрові системи Rust можуть викликати узгоджені сервіси ядра, але не повинні залежати від Android UI.
- Рендерер отримує підготовлені дані для малювання, а не змінює правила гри.
- Python tooling працює з файлами даних і схемами, а не напряму з пам’яттю запущеного рушія.
- Assembly викликається через вузькі, документовані функції й не знає про всю архітектуру рушія.

### 6.2. Команди та події

Варто розрізняти два типи повідомлень:

- **Команда** — запит виконати конкретну дію, наприклад перемістити персонажа, активувати об’єкт або змінити налаштування.
- **Подія** — факт, який уже стався, наприклад об’єкт активовано, двері змінили стан або рівень завантажено.

Команди перевіряються відповідною системою та можуть бути відхилені. Події повідомляють іншим системам про результат і можуть запускати додаткові правила.

Для уникнення циклів і непередбачуваної поведінки система подій має мати визначений порядок обробки, правила щодо подій, створених під час обробки інших подій, і захист від нескінченних каскадів.

### 6.3. Контракти даних

Для кожного типу даних потрібно задокументувати:

- назву й призначення;
- стабільний ідентифікатор;
- обов’язкові та необов’язкові поля;
- допустимі типи й діапазони значень;
- семантику полів;
- поведінку за відсутнього або невідомого значення;
- правила сумісності версій;
- повідомлення про помилки валідації.

Поля, значення яких використовуються в кількох підсистемах, мають визначатися один раз у схемі або спільному описі, а не копіюватися вручну в Rust, Python, Kotlin і Assembly.

## 7. Модель світу, об’єктів, правил і подій

Цей розділ описує цільову модель і спирається на напрям уже наявного прототипу. Точні типи й поля мають бути звірені з фактичним кодом до оголошення стабільного формату.

### 7.1. Об’єкт світу

Об’єкт має мати стабільний ID та тип. Додаткові властивості можуть описувати стан, зв’язок з іншим об’єктом, доступність або інші параметри.

У поточному прототипному напрямі вже використовувалася таблична модель із полями на кшталт:

- `ID` — ідентифікатор об’єкта;
- `TYPE` — тип;
- `STATE` — поточний стан;
- `LINK` — зв’язок або посилання;
- `ACCESS` — ознака доступності чи режим доступу.

Це лише зафіксований напрямок моделі, а не остаточна специфікація. Перед перенесенням до Rust потрібно визначити точний зміст кожного поля, його тип, допустимі значення та правила посилань.

### 7.2. Правило

Правило описує умову й дію, які мають бути виконані у відповідь на певний контекст. У загальному вигляді:

1. визначити джерело або тип події;
2. перевірити поле об’єкта та очікуване значення;
3. визначити ціль — об’єкт або підсистему;
4. визначити поле, над яким дозволена дія;
5. виконати дію з указаним значенням;
6. зафіксувати результат і, за потреби, створити подію.

У попередньому форматі прототипу зустрічалися поля на кшталт `SOURCE_TYPE`, `CHECK_FIELD`, `CHECK_VALUE`, `TARGET_MODE`, `TARGET_FIELD`, `ACTION` і `VALUE`. Їхній остаточний словник треба зберегти в окремій специфікації формату, включно з таблицями допустимих кодів і правилами перевірки.

### 7.3. Подія

Подія повинна мати визначене джерело, тип, дані та зрозумілий етап життєвого циклу. Необхідно вирішити, чи кожна подія зберігає лише посилання на об’єкт, чи також містить знімок значень на момент виникнення. Це важливо, бо стан об’єкта може змінитися до того, як подія буде оброблена.

### 7.4. Черга подій

Черга подій має гарантувати:

- визначений порядок отримання й обробки;
- явне поводження з переповненням;
- перевірку коректності індексів і розмірів;
- визначену поведінку під час скидання або перезапуску рівня;
- відстеження кількості створених, оброблених і відхилених подій;
- захист від нескінченних ланцюгів подій.

Розмір черги не слід обирати лише навмання. На ранньому етапі можна залишити фіксований розмір, як у прототипі, але перевіряти переповнення й записувати діагностику. Пізніше місткість можна обґрунтувати тестами або перейти до іншої стратегії.

## 8. Формати зберігання та передавання даних

### 8.1. Файли даних

На першому етапі основним форматом ігрових даних обрано JSON. Детальна структура, правила валідації та міграції з поточного текстового формату визначені в `DATA_FORMAT.md`. TOML і YAML не підтримуються як рівнозначні runtime-формати; за потреби додатковий авторський формат можна розглянути пізніше.

Рекомендація для першої версії: не підтримувати два конкуруючі формати як рівнозначні. Один формат можна використовувати як вихідний, а інший — лише як внутрішній результат конвертації, якщо це буде справді потрібно.

### 8.2. Версії

Кожен рівень або пакет даних має мати поле версії схеми, наприклад `schema_version`. Завантажувач повинен:

- приймати підтримувані версії;
- видавати зрозумілу помилку для невідомої версії;
- за можливості відокремлювати міграцію старих даних від звичайного завантаження;
- не трактувати невідомі числові коди дій чи типів як довільні допустимі значення.

### 8.3. Внутрішній формат виконання

Після завантаження дані перетворюються на структури, зручні для Rust-ядра. Вони не обов’язково мають зберігати текстову форму. У майбутньому можна використовувати компактний бінарний формат, якщо вимірювання покажуть, що це потрібно для часу завантаження, розміру або пам’яті.

### 8.4. Дані на межі FFI

Через JNI або C ABI не слід безпосередньо передавати внутрішні `Vec`, `String`, `HashMap` чи інші типи Rust, внутрішнє представлення яких не є контрактом для іншої мови. Натомість потрібно використовувати:

- примітиви фіксованої ширини;
- структури з явно задекларованим C-сумісним представленням, якщо це доречно;
- дескриптори/handle для об’єктів, якими володіє Rust;
- функції створення, доступу й звільнення ресурсів із чіткими правилами володіння;
- буфери з явною довжиною та документованою відповідальністю за пам’ять.

Жодна сторона не повинна звільняти пам’ять, якою за контрактом володіє інша сторона.

## 9. Ігровий цикл і графічний кадр

Точна частота симуляції та схема потоків визначаються під час прототипування. Початково варто розділити логічне оновлення світу та відображення кадру.

Приблизний цикл:

1. Android-платформа збирає сенсорний ввід.
2. Kotlin передає ядру зведені команди та інформацію про час кадру.
3. Rust нормалізує ввід і формує внутрішні команди.
4. Система подій приймає нові події.
5. Система правил перевіряє умови й застосовує допустимі дії.
6. Світ оновлює стани об’єктів.
7. Ядро готує узгоджені дані для відображення.
8. Рендерер Rust використовує OpenGL ES для відправлення графічних команд.
9. GLSL ES-шейдери виконуються на GPU, і кадр з’являється на поверхні.
10. Діагностична система за потреби записує час і результат ключових етапів.

На ранній стадії можна запускати логічне оновлення й рендеринг послідовно, щоб зменшити складність синхронізації. Окремі потоки для симуляції, завантаження даних або аудіо слід додавати лише після визначення необхідності.

### Важливі часові правила

- Пауза застосунку має зупиняти або переводити симуляцію в визначений режим.
- Повернення з фону не повинно спричиняти неконтрольовано великий стрибок часу симуляції.
- Треба визначити, чи логічне оновлення використовує фіксований крок часу, змінний крок або комбінований підхід.
- Дельту часу слід перевіряти й обмежувати згідно з обраною моделлю.
- Втрата графічного контексту не повинна автоматично скидати світ або чергу подій, якщо це не передбачено логікою гри.

## 10. Потоки, пам’ять і ресурси

### 10.1. Потоки

Потік, на якому дозволені OpenGL-виклики, визначається способом створення EGL-контексту. Рендерер не повинен викликати OpenGL з іншого потоку без явного перенесення контексту та відповідної синхронізації.

На першому етапі рекомендовано мати якомога менше потоків: UI-потік Android, графічний потік і, за потреби, окрему роботу з файлами. Усі правила доступу до спільного стану потрібно документувати.

### 10.2. Володіння пам’яттю

Усередині Rust варто використовувати природні для нього правила володіння та запозичення. Межі C ABI/ JNI не повинні руйнувати цю модель: ресурси передаються як handle або через функції, що чітко визначають власника.

### 10.3. Графічні ресурси

Текстури, шейдерні програми, буфери та інші ресурси GPU мають мати явний життєвий цикл. Їх потрібно створювати після появи контексту, перевіряти результат створення, коректно звільняти, коли контекст чинний, і відновлювати після його втрати.

### 10.4. Обмеження мобільного пристрою

Необхідно контролювати:

- пікове використання пам’яті;
- розмір завантажених ресурсів;
- частоту повторних виділень пам’яті;
- тривалість обробки кадру;
- кількість JNI-викликів;
- час завантаження рівня;
- нагрівання й стабільність тривалої роботи.

Ці показники мають вимірюватися на цільовому пристрої, а не лише на настільній системі.

## 11. Обробка помилок і діагностика

Для кожної підсистеми треба визначити, як вона повідомляє про помилки. Мінімальні категорії:

- помилки читання файлу;
- помилки синтаксису або валідації даних;
- невідомі типи, дії чи ідентифікатори;
- недійсні переходи станів;
- переповнення черги подій;
- помилки ініціалізації ядра;
- помилки JNI/ABI;
- помилки створення графічних ресурсів або шейдерів;
- втрати чи відновлення графічного контексту.

Помилка не повинна мовчки перетворюватися на успішний результат. Для очікуваних помилок потрібні контрольовані коди або значення результату. Для критичних помилок треба визначити, чи можна безпечно зупинити рівень, перезапустити підсистему або завершити застосунок із діагностикою.

Логи мають бути корисними в Termux і в Android-версії. Доцільно використовувати спільні рівні журналювання (наприклад, `ERROR`, `WARN`, `INFO`, `DEBUG`) і префікс/назву підсистеми. У збірці для звичайного користувача докладність можна зменшити.

## 12. Локалізація людськими мовами

Мови програмування та мови інтерфейсу — дві різні задачі. Оскільки рушій планується модульним, локалізацію варто зробити окремим шаром даних, а не вбудовувати тексти в логіку.

Рекомендована концепція:

- ключі текстів стабільні й не залежать від мови;
- переклади зберігаються в ресурсах локалізації;
- українська може бути початковою базовою локаллю;
- додавання іншої мови не змінює логіку правил або типи об’єктів;
- формат має враховувати параметризовані повідомлення та, якщо буде потрібно, правила множини;
- відсутній переклад має давати визначений fallback, а не ламати сцену або інтерфейс.

Наприклад, внутрішня дія має посилатися на ключ `door.locked`, а не зберігати український чи англійський текст безпосередньо в коді.

## 13. Пропонована структура репозиторію

Це **цільовий ескіз**, а не вимога негайно перемістити всі наявні файли. Під час міграції можна зберегти поточну структуру й переносити компоненти поетапно.

```text
project-root/
├── README.md
├── ARCHITECTURE_MODULAR_GAME_ENGINE.md
├── build.sh                    # поточний/початковий шлях збирання в Termux

├── src/                        # існуючий прототип — до завершення міграції
│   ├── world.S
│   ├── events.S
│   ├── rules.S
│   ├── main_rules.S
│   └── level_loader.c
├── engine/                     # цільова організація Rust-ядра
│   ├── Cargo.toml
│   └── src/
│       ├── lib.rs
│       ├── engine.rs
│       ├── world/
│       ├── events/
│       ├── rules/
│       ├── input/
│       ├── data/
│       ├── resources/
│       ├── render/
│       ├── ffi/
│       └── diagnostics/
├── android/                    # Android-застосунок і Kotlin-оболонка
│   └── app/src/main/
│       ├── java/...
│       ├── res/

│   ├── shaders/

│   │   └── basic.frag
```

- Каталоги `engine/`, `android/` та `native/` є цільовим поділом, не обов’язково першою дією.
- Для Rust варто почати з одного crate, а не дробити ядро на багато crate без практичної потреби.
- `assets/` призначений для ресурсів, потрібних рушію; `data/` — для декларативної ігрової логіки та описів світу.
- Згенеровані файли й артефакти збірки не мають змішуватися з вихідними даними.
- Актуальний `build.sh` можна зберегти, поки Termux є основним середовищем розробки.

## 14. Збирання й робочий процес

### 14.1. Поточний етап: Termux / ARM64

Початковий процес має залишатися простим і повторюваним:

1. Перевірити вихідні файли.
2. Зібрати асемблерні модулі Clang для AArch64.
3. Зібрати потрібні C-модулі.
4. Скомпонувати прототип.
5. Запустити тести або контрольний сценарій.
6. Перевірити лог і результат.

Коли Rust-ядро стане частиною прототипу, його слід додати до процесу окремим кроком і перевірити сумісність цільового triple, лінкування та ABI. Конкретні прапорці збирання необхідно зафіксувати після реальної перевірки в Termux.

### 14.2. Майбутній Android-процес

Коли буде готова Android-оболонка:

- Gradle збирає Kotlin-застосунок і пакує ресурси;
- Cargo збирає Rust-бібліотеку для потрібної Android ABI;
- JNI/NDK-міст забезпечує узгоджену точку входу;
- шейдери й інші ресурси додаються до пакета або копіюються у доступне застосунку сховище;
- окремо перевіряються встановлення, старт, пауза, відновлення, рендеринг і логування на фізичному пристрої.

Gradle і Cargo можуть координуватися через скрипти або плагіни, але остаточна схема залежить від того, який інструментарій буде обрано. Не варто вигадувати остаточну систему збірки до появи мінімального Android-прототипу.

## 15. Тестування

### 15.1. Unit-тести ядра

Без запуску графіки мають тестуватися:

- створення об’єкта й початковий стан;
- допустимі та недопустимі переходи станів;
- перевірка правил;
- застосування дій;
- порядок подій;
- поведінка черги при заповненні;
- завантаження й валідація даних;
- скидання стану між рівнями.

### 15.2. Контрольні сценарії

Для прототипу варто зберігати невеликі відтворювані сценарії: початковий стан, команда, очікувані події та очікуваний результат. Це дозволить переносити частини з Assembly або C у Rust і порівнювати результати старої та нової реалізацій.

### 15.3. Інтеграційні тести

Перевіряти:

- виклик нативного ядра з Kotlin;
- коректність передавання команд вводу;
- завантаження рівня з пакета ресурсів;
- створення графічного контексту й відображення контрольного кадру;
- поведінку після паузи та відновлення;
- відновлення ресурсів після перевідтворення графічного контексту;
- узгодженість версії файлів даних зі схемою ядра.

### 15.4. Перевірки даних у Python

Python-валідатор має мати автоматизовані тести на типові помилки: відсутній ID, повторний ID, посилання на невідомий об’єкт, невідомий код дії, поле неправильного типу, неузгоджена версія схеми та некоректне значення.

### 15.5. Критерій для Assembly

Для кожної оптимізованої асемблерної функції потрібні:

- функціональний тест;
- тест граничних значень;
- опис ABI;
- порівняння з простою еталонною реалізацією, якщо вона є;
- замір продуктивності, якщо функція обґрунтовується швидкодією.

## 16. План реалізації

### Етап 0 — зафіксувати наявний прототип

- Зберегти контрольну робочу версію.
- Документувати функції й ABI наявних `.S` та C-файлів.
- Записати формат об’єктів і подій, який реально використовує прототип.
- Додати тестові сценарії, які підтверджують поточну поведінку.

**Результат:** є перевірена вихідна точка, з якою можна порівнювати міграцію.

### Етап 1 — узгодити контракти даних

- Визначити точні значення типів, станів, полів і кодів дій.
- Визначити формат файлів даних і версію схеми.
- Визначити правила обробки помилок і невідомих полів.
- Зробити Python-валідатор і набір помилкових/правильних прикладів.

**Результат:** формат даних можна перевіряти незалежно від ігрового коду.

### Етап 2 — створити мінімальне Rust-ядро

- Створити crate із публічним API.
- Реалізувати мінімальні типи об’єктів, правил і подій.
- Написати тести, що повторюють узгоджені сценарії прототипу.
- На цьому кроці не додавати складний рендеринг або Android-специфічні залежності.

**Результат:** ядро можна збирати й тестувати окремо в Termux.

### Етап 3 — інтегрувати наявний низькорівневий код

- Для кожної функції вирішити, чи залишити її в Assembly, перенести в Rust або тимчасово викликати через C ABI.
- Визначити формальні сигнатури й правила пам’яті.
- Порівняти результати з контрольними сценаріями.
- Не переносити все одразу без тестів.

**Результат:** Rust координує ядро, а низькорівневі фрагменти мають вузькі й перевірені межі.

### Етап 4 — підготувати дані та цикл симуляції

- Підключити завантаження рівнів.
- Додати правила й чергу подій.
- Визначити поведінку часових кроків і паузи.
- Додати базові логи й діагностику.

**Результат:** рушій виконує логічний сценарій без потреби в графіці.

### Етап 5 — мінімальний графічний прототип

- Створити базовий рендерер OpenGL ES.
- Завантажити найпростіші GLSL ES-шейдери.
- Вивести контрольну сцену.
- Перевірити створення, втрату й відновлення контексту.
- Передавати рендереру мінімальне підготовлене представлення світу.

**Результат:** ядро та рендерер працюють разом, але залишаються логічно відокремленими.

### Етап 6 — інтеграція Kotlin/Android

- Створити мінімальний Android-проєкт.
- Під’єднати Rust через JNI.
- Передавати команди вводу й події життєвого циклу.
- Перевірити паузу, відновлення та обробку повернення з фону.
- Перевірити керування на смартфоні та доступність критичних елементів інтерфейсу.

**Результат:** запускається мінімальна Android-версія, яка керує нативним рушієм.

### Етап 7 — розширення та оптимізація

- Виміряти продуктивність на цільовому пристрої.
- Визначити реальні вузькі місця.
- Оптимізувати потрібні ділянки Rust або Assembly.
- Додати решту графічних ефектів, ресурси, локалізацію та інструменти за пріоритетом.

**Результат:** розширення спирається на перевірені межі та фактичні вимірювання.

## 17. Критерії приймання початкової архітектури

Початкову архітектуру можна вважати достатньо оформленою для першої реалізації, коли:

- ролі Kotlin, Rust, GLSL ES, Python і Assembly документовані;
- формат об’єктів, правил і подій має однозначний опис;
- визначено, який компонент є власником активного стану світу;
- межі JNI та C ABI не передають неузгоджені внутрішні структури;
- існує відтворюваний сценарій, який перевіряє базові правила;
- дані можна перевірити без запуску гри;
- ядро можна протестувати без графічної підсистеми;
- графічний код не змішується з правилами світу;
- є опис життєвого циклу Android і втрати графічного контексту;
- кожна наступна стадія може бути реалізована без необхідності переписувати всі попередні.

## 18. Основні ризики й способи їх зменшення

| Ризик | Чому це важливо | Спосіб зменшення |
|---|---|---|
| Надлишок мов і меж | Зростає складність збірки, налагодження та передачі даних | Додавати мову лише для чіткої ролі; спочатку створити мінімальні вертикальні прототипи |
| Rust і Assembly одночасно керують станом | Можливі розбіжності й складне налагодження | Rust є власником стану; Assembly надає вузькі функції |
| Python стає обов’язковим у runtime | Збільшується складність Android-пакування й підтримки | Починати з офлайн-інструментів; вбудовувати інтерпретатор лише за обґрунтованої потреби |
| Передчасний бінарний формат | Важче редагувати й знаходити помилки | Почати з читабельного формату та перейти до бінарного за результатами вимірювань |
| JNI викликається для кожного дрібного елемента | Додаються накладні витрати й складність | Робити виклики крупнозернистими: команда/кадр/пакет, а не об’єкт/операція |
| Невизначений графічний контекст | OpenGL-виклики можуть виконуватися не на тому потоці | Зафіксувати модель контексту та перевірити її раннім прототипом |
| Відсутність тестів під час міграції | Важко відрізнити нову помилку від старої поведінки | До перенесення зафіксувати контрольні сценарії й результати |
| Асемблер без доведеної користі | Код стає складнішим без виграшу | Тестувати коректність і вимірювати швидкодію кожної оптимізації |
| Один формат даних без версій | Зміни схеми ламають старі рівні | Ввести `schema_version` і правила сумісності від початку |

## 19. Рішення, які ще треба перевірити

Ці питання відкриті й не повинні непомітно вважатися вже вирішеними:

1. **Основний формат ігрових даних:** JSON обрано для першого етапу; відкритим залишається лише остаточне уточнення схеми на основі чинного коду.
2. **Модель Android-графіки:** Kotlin `GLSurfaceView` із викликом Rust на активному GL-потоці чи нативне керування EGL.
3. **Межа C/JNI:** прямий JNI у Rust, невеликий C-міст або інша обрана інтеграційна схема.
4. **Доля C-завантажувача:** залишити тимчасово, переписати на Rust або використати як незалежний перевірений модуль.
5. **Доля кожної асемблерної функції:** залишити, замінити Rust-реалізацією або оптимізувати після профілювання.
6. **Часова модель симуляції:** фіксований крок, змінний крок чи комбінована модель.
7. **Модель подій:** фіксована черга, динамічна черга або інша структура після вимірювань.
8. **Межа між Rust-ядром і рендерером:** які саме структури складають знімок сцени.
9. **Формат локалізації:** окремі JSON/TOML-ресурси чи формат ресурсів Android для частини інтерфейсу.
10. **Структура Cargo workspace:** один crate для прототипу чи кілька crate після появи реальних меж модулів.

Для кожного такого рішення треба записати коротке обґрунтування після перевірки, а не ускладнювати архітектуру наперед.

## 20. Підсумкова концепція

Цільова схема розподіляє роботу між компонентами за їхніми сильними сторонами:

- Kotlin утримує Android-рівень і взаємодію з користувачем;
- Rust володіє станом світу, правилами та координацією;
- Rust-рендерер керує OpenGL ES, а GLSL ES описує програми для GPU;
- Python готує й перевіряє дані та підтримує інструменти розробки;
- ARM64 Assembly залишається спеціалізованим низькорівневим компонентом із вузьким ABI;
- декларативні файли відокремлюють вміст гри від реалізації рушія;
- JNI та C ABI утворюють контрольовані межі між різними мовами;
- тести й контрольні сценарії дозволяють поступово переходити від поточного прототипу до нової архітектури.

Ключове правило проєкту: **модуль можна замінити або розвивати незалежно, якщо його контракт залишається стабільним**. Тому перший практичний крок — не писати всі підсистеми одночасно, а зафіксувати поточну поведінку прототипу, узгодити формати даних і створити мінімальне Rust-ядро, яке можна перевіряти без графіки та Android-оболонки.

## Додаток A. Короткий словник

- **ABI (Application Binary Interface):** правила виклику скомпільованих функцій, передавання аргументів, повернення результатів і роботи з регістрами та пам’яттю.
- **C ABI:** поширений низькорівневий контракт для взаємодії скомпільованого коду різними мовами.
- **FFI (Foreign Function Interface):** механізм виклику функцій або використання даних з іншої мови програмування.
- **JNI (Java Native Interface):** механізм взаємодії Java/Kotlin-коду з нативним кодом Android.
- **OpenGL ES:** графічний API для вбудованих і мобільних платформ.
- **GLSL ES:** мова шейдерів, що використовуються з OpenGL ES.
- **GPU:** графічний процесор.
- **Renderer / рендерер:** система, яка готує та відправляє графічні команди.
- **Runtime:** компоненти, що виконуються безпосередньо під час роботи гри.
- **Tooling:** допоміжні інструменти розробки, перевірки й підготовки ресурсів.
- **Schema / схема даних:** формальний опис структури й допустимих значень файлу даних.
- **Handle:** непрямий ідентифікатор ресурсу, яким керує певний компонент.
