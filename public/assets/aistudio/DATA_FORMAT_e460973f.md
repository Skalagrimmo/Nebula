## 1. Призначення

Цей документ визначає, як зберігати, перевіряти, передавати та завантажувати дані гри в модульному рушії. Він є продовженням архітектурної документації й закріплює рішення використовувати **JSON як основний формат даних першої версії**.

JSON обрано не тому, що він ідеальний для будь-яких задач, а тому, що він має прості правила, підтримується стандартними інструментами Python і має зрілі бібліотеки для Rust та Kotlin. YAML не вводиться на першому етапі: другий формат означав би додаткові правила валідації, конвертації та тестування. За потреби YAML можна додати пізніше як зручний формат авторського редагування, не змінюючи внутрішньої моделі даних рушія.

Специфікація враховує наявний прототип, у якому таблиця об'єктів має поля:

```text
# OBJECT ID TYPE STATE LINK ACCESS
object 1 1 0 2 1
object 2 2 0 0 0
object 3 3 0 4 0
object 4 4 0 0 0
object 5 3 0 6 0
object 6 4 0 0 0
```

Також наявний текстовий формат правил із заголовком на зразок:

```text
# EVENT SOURCE_TYPE CHECK_FIELD CHECK_VALUE TARGET_MODE TARGET_FIELD ACTION VALUE
```

Ці рядки наведено як опис поточної форми даних, а не як новий формат для майбутніх рівнів. На час міграції старі файли залишаються контрольним джерелом поведінки. Остаточні значення та семантика числових кодів мають бути перевірені за завантажувачем і асемблерними модулями, перш ніж вводити для них іменовані константи.

## 2. Цілі та обмеження

Формат має:

1. Бути читабельним для людини та зручним для редагування вручну.
2. Мати явні назви полів, щоб значення не залежали лише від позиції у рядку.
3. Підтримувати перевірку структури й логічної цілісності до запуску гри.
4. Мати номер версії схеми, щоб майбутні зміни можна було контролювати.
5. Бути незалежним від мови, яка обробляє дані: Python перевіряє та готує файли, Rust завантажує їх і керує активним станом світу.
6. Бути придатним до міграції з поточного текстового формату без одночасного переписування всіх ігрових систем.
7. Не вимагати від Android-застосунку наявності Python у час виконання.

У першій версії формат описує базові метадані рівня, об'єкти та правила. Він **не намагається** одразу описати кожну майбутню систему рушія. Матеріали, аудіо, локалізація, анімаційні графи, сценарії користувачів і мережеві дані можуть отримати окремі специфікації, коли для них з'явиться реальна потреба.

## 3. Розподіл відповідальності

| Компонент | Відповідальність |
|---|---|
| JSON-файли | Декларативне зберігання вихідних даних рівня |
| Python-інструменти | Перевірка, діагностика, конвертація та майбутні інструменти авторингу |
| Rust | Повторна перевірка критичних умов, завантаження й перетворення даних у внутрішні структури рушія |
| Kotlin | Використання публічного API рушія; не є джерелом істини для стану об'єктів |
| GLSL ES | Отримує графічні ресурси й параметри через рендерер; безпосередньо JSON не читає |
| ARM64 Assembly | Працює з визначеним низькорівневим представленням даних, коли це потрібно; не парсить JSON |

JSON не передається між Kotlin і Rust на кожному кадрі. Файл читається під час завантаження рівня або іншої визначеної операції. Після перевірки Rust створює потрібні структури в пам'яті, а під час гри системи працюють із ними.

## 4. Загальні правила JSON

### 4.1. Кодування й синтаксис

- Кодування файлів — UTF-8.
- Використовується стандартний JSON, без коментарів і без кінцевих ком у масивах чи об'єктах.
- Ключі об'єктів мають бути унікальними. Повторення ключа в одному об'єкті вважається помилкою.
- Рядки беруться в подвійні лапки.
- Булеві значення записуються як `true` або `false`, порожнє значення — як `null`.
- Числові поля, які описані як цілі, повинні бути цілими числами JSON. Значення `1.0` не слід використовувати замість `1`.
- Коментарі до вихідних даних зберігаються в документації або в окремих описових полях, а не у вигляді `//` чи `#` усередині JSON.

### 4.2. Назви полів

Назви ключів використовують `snake_case`, наприклад `schema_version`, `type_id` і `link_id`. Після публікації версії схеми назви ключів вважаються частиною контракту. Не слід перейменовувати їх без зміни версії схеми або спеціально визначеної міграції.

### 4.3. Ідентифікатори

- Ідентифікатор об'єкта `id` — додатне ціле число й унікальний у межах рівня.
- Значення `0` у старому полі `LINK` означає відсутність зв'язку в поточному прототипі. У JSON воно нормалізується до `"link_id": null`.
- У JSON `null` ідентифікатора зв'язку не є об'єктом з ID `0`; це явний знак відсутності посилання.
- Якщо `link_id` містить число, воно має посилатися на наявний об'єкт того самого рівня, якщо окремий майбутній тип зв'язку не визначатиме інше.
- ID об'єктів не перевикористовуються для двох різних об'єктів в одному рівні.
- Текстові ID рівня та правила мають використовувати стабільні короткі ключі, а не випадкові назви, залежні від позиції рядка.

### 4.4. Порядок елементів

JSON-масиви зберігають порядок елементів. Особливо важливо зберігати порядок `rules`: якщо поточна реалізація перевіряє правила послідовно, зміна порядку під час конвертації може змінити поведінку гри. Автоматичне сортування правил за ID заборонене, поки семантика виконання не буде окремо підтверджена.

Порядок об'єктів також слід зберігати під час першої міграції, навіть якщо їхня семантика формально не має залежати від позиції в масиві. Це спрощує зіставлення результатів старого й нового завантажувачів.

## 5. Структура файлу рівня

Один файл описує один рівень або один самодостатній набір даних, який можна завантажити як рівень.

### 5.1. Кореневий об'єкт

| Поле | Тип | Обов'язкове | Призначення |
|---|---|---:|---|
| `format` | рядок | так | Маркер типу документа: `modular-game-engine-level` |
| `schema_version` | ціле число | так | Версія схеми даних; у першому варіанті — `1` |
| `level` | об'єкт | так | Метадані рівня |
| `objects` | масив об'єктів | так | Визначення об'єктів рівня |
| `rules` | масив правил | так | Визначення правил/подій рівня; може бути порожнім |

Невідомі кореневі ключі у версії 1 мають викликати помилку валідації, а не мовчки ігноруватися. Це допомагає виявляти друкарські помилки. Нове поле додається через контрольовану зміну схеми.

### 5.2. Приклад мінімального файлу

Нижче — приклад валідного за структурою документа. Числові ID типів і поля показані як значення з наявного прототипу; їхнє прикладне значення не декларується цим прикладом.

      "access": 1

    {
      "id": 2,
      "type_id": 2,
      "state": 0,
      "link_id": null,
      "access": 0
    },
    {
      "id": 3,
      "type_id": 3,
      "state": 0,
      "link_id": 4,
      "access": 0
    },
    {
      "id": 4,
      "type_id": 4,
      "state": 0,
      "link_id": null,
      "access": 0
    },
    {
      "id": 5,
      "type_id": 3,
      "state": 0,

      "access": 0

Цей файл відтворює наведені шість рядків таблиці об'єктів з очевидною нормалізацією: значення `LINK = 0` стає `link_id = null`. Він ще не включає правила з прототипу, тому що точну відповідність усіх полів правила і їхню семантику потрібно звірити з наявним кодом.

## 6. Метадані рівня

Об'єкт `level` у версії 1 має такі поля:

| Поле | Тип | Обов'язкове | Правила |
|---|---|---:|---|
| `id` | рядок | так | Стабільний ключ рівня; латинські малі літери, цифри, `_` і `-`; перший символ — літера або цифра |
| `name` | рядок | так | Людиночитна назва, непорожня після видалення крайніх пробілів |
| `description` | рядок | ні | Короткий опис для редактора або діагностики |

У першій версії не додаємо сюди параметри рендерера, керування, локалізацію чи внутрішні стани гри. Це окремі відповідальності, які можна буде формалізувати після появи потреби.

`level.id` має залишатися стабільним навіть тоді, коли `name` змінюється. На нього згодом можуть посилатися меню вибору рівнів, збереження та тестові сценарії.

## 7. Об'єкти

### 7.1. Поля об'єкта версії 1

| Поле JSON | Тип | Обов'язкове | Відповідність прототипу | Примітка |
|---|---|---:|---|---|
| `id` | ціле число | так | `ID` | Унікальний ID об'єкта, більший за нуль |
| `type_id` | ціле число | так | `TYPE` | Числовий код типу; словник кодів ще треба звірити з реалізацією |
| `state` | ціле число | так | `STATE` | Поточне початкове значення стану; допустимі значення залежать від типу/логіки |
| `link_id` | ціле число або `null` | так | `LINK` | ID пов'язаного об'єкта або `null`, якщо зв'язку немає |
| `access` | ціле число | так | `ACCESS` | Числове поле доступу з поточного формату; значення та дозволені діапазони підтвердити за кодом |

У версії 1 не перейменовуємо числові поля `type_id`, `state`, `access` у припущені семантичні enum-и. Спершу треба документувати реальні коди з завантажувача, `world.S`, `events.S`, `rules.S` та пов'язаних файлів. Коли словник буде підтверджено, над JSON можна додати зручні назви як авторський синтаксис або інструментальну абстракцію, але це має бути окремим узгодженим рішенням.

### 7.2. Правила цілісності об'єктів

Валідатор має перевіряти:

1. Кожен об'єкт є JSON-об'єктом, а не рядком або числом.
2. Усі п'ять полів присутні й мають правильний тип.
3. `id` є додатним цілим числом; ID не дублюється.
4. `type_id`, `state` та `access` — цілі числа; `type_id` має відповідати реєстру типів, коли такий реєстр буде документовано.
5. `link_id` дорівнює `null` або містить допустимий ID об'єкта, на який посилається рівень.
6. Посилання на відсутній об'єкт є помилкою, якщо тільки майбутній формат явно не дозволить зовнішні посилання.
7. У першій міграції не видаляються непізнані числові значення і не замінюються довільними дефолтами.

Циклічні зв'язки не забороняються автоматично. Спершу слід підтвердити, чи можуть вони бути коректними для ігрової логіки. Самопосилання також має принаймні породжувати діагностичне попередження, якщо воно не описане як допустима конструкція.

### 7.3. Відсутність зв'язку

Старий формат використовує `0` як відсутнє значення у `LINK`. У JSON використовується `null`, тому що він явно описує відсутність посилання й не плутається зі справжнім ID.

Правило конвертації:

```text
legacy LINK = 0      -> JSON link_id = null
legacy LINK = N > 0  -> JSON link_id = N
JSON link_id = null  -> legacy LINK = 0, якщо потрібен зворотний експорт
JSON link_id = N     -> legacy LINK = N
```

Під час міграції потрібно перевірити, чи `0` зарезервовано лише як маркер відсутності зв'язку в усіх гілках наявного коду. Якщо знайдеться інше застосування нуля, правило слід уточнити до автоматичної конвертації.

## 8. Правила та події

### 8.1. Модель першої версії

Поточний текстовий заголовок задає такі поля правила:

```text
EVENT SOURCE_TYPE CHECK_FIELD CHECK_VALUE TARGET_MODE TARGET_FIELD ACTION VALUE
```

Ключове слово `event`/`EVENT` у текстовому файлі є маркером запису, а не обов'язково окремим полем даних. У JSON кожне правило є об'єктом з явними ключами. Для збереження сумісності з поточним низькорівневим представленням коди на першому етапі залишаються цілими числами.

### 8.2. Поля правила JSON

| Поле JSON | Тип | Відповідність заголовку прототипу | Що потрібно підтвердити |
|---|---|---|---|
| `id` | рядок | Нове поле лише для даних/діагностики | Стабільний унікальний ключ правила; може не передаватися в стару runtime-структуру |
| `source_type_id` | ціле число | `SOURCE_TYPE` | Реєстр кодів типів джерела |
| `check_field_id` | ціле число | `CHECK_FIELD` | Реєстр полів, які можуть перевірятися |
| `check_value` | ціле число | `CHECK_VALUE` | Допустимий діапазон і правила порівняння |
| `target_mode_id` | ціле число | `TARGET_MODE` | Реєстр режимів вибору цілі |
| `target_field_id` | ціле число | `TARGET_FIELD` | Реєстр полів, які дозволено змінювати |
| `action_id` | ціле число | `ACTION` | Реєстр дій і семантика кожної дії |
| `value` | ціле число | `VALUE` | Значення, яке використовує відповідна дія |

`id` правила додається для діагностики: повідомлення про помилку зможе посилатися на `rule_terminal_activation`, а не лише на позицію в масиві. У першій версії цей ключ може бути відсутнім у внутрішній структурі виконання, якщо наявний код не потребує його. Якщо конвертація генерує старий позиційний файл, порядок рядків зберігається.

### 8.3. Приклад форми правила

Нижче наведено лише приклад структури. Числа `1` не закріплюють реальні коди типів, полів, режимів або дій — до їх перевірки за джерельним кодом вони є умовними значеннями.

```json
{
  "id": "rule_example_001",
  "source_type_id": 1,
  "check_field_id": 1,
  "check_value": 1,
  "target_mode_id": 1,
  "target_field_id": 1,
  "action_id": 1,
  "value": 1
}
```

### 8.4. Вимоги до перевірки правил

Валідатор першої версії перевіряє:

- усі обов'язкові поля правила наявні;
- `id` правила унікальний серед правил рівня й відповідає формату текстових ID;
- кодові поля є цілими числами, а не рядками чи числами з дробовою частиною;
- правила зберігають початковий порядок;
- після появи реєстрів кожен числовий код існує у відповідному реєстрі;
- після документування семантики можна перевіряти сумісність полів і дій, наприклад чи дозволено конкретній дії змінювати конкретне поле.

До перевірки коду не слід здогадуватися, що означають числові значення `CHECK_FIELD`, `TARGET_MODE` або `ACTION`. Спочатку потрібно зіставити їх з інструкціями в `rules.S` і способом завантаження рядків. Це запобігає помилці, коли добре читабельний, але семантично неправильний JSON замінює стару робочу поведінку.

## 9. Реєстри кодів

Щоб числові коди не залишалися набором незрозумілих констант, варто поступово додати реєстри. Це не означає, що всі реєстри треба створити до першого JSON-файлу. Спочатку слід витягти з чинного коду фактичні значення й підтвердити їхні значення.

Можлива майбутня структура:

```text
data/
  registries/
    object_types.json
    object_fields.json
    target_modes.json
    rule_actions.json
```

Приклад можливої форми реєстру (поля умовні; числові значення тут не визначають коди рушія):

```json
{
  "registry": "object_types",
  "schema_version": 1,
  "entries": [
    {
      "id": 1,
      "key": "example_type",
      "description": "Приклад запису; замінити підтвердженим типом"
    }
  ]
}
```

Правила для реєстрів:

1. Числові ID мають бути унікальними в межах відповідного реєстру.
2. Після публікації ID не можна повторно призначати іншому значенню без міграції даних.
3. `key` — стабільний машинний ключ; `description` — пояснення для людей.
4. Числові значення в реєстрах мають походити з перевіреної реалізації, а не з припущень за прикладами.
5. Якщо імена або опис змінюються, незмінний числовий ID продовжує визначати старі дані.

Реєстри можуть почати як Python-константи, якщо так простіше під час дослідження коду. Коли структура стабілізується, їх доцільно винести у файли, які можуть читати валідатор і тестові інструменти.

## 10. Версіонування схеми

### 10.1. Поле `schema_version`

Кожен файл містить:

```json
{
  "schema_version": 1
}
```

Це версія **формату файлу**, а не версія гри, рушія чи рівня. Номер версії обробляється явно: завантажувач не повинен мовчки трактувати невідому версію як версію 1.

### 10.2. Коли змінювати версію

Версію слід підвищувати, якщо зміна:

- перейменовує або вилучає обов'язкове поле;
- змінює тип поля або його семантику;
- змінює значення спеціального маркера, зокрема значення відсутнього посилання;
- змінює структуру правил так, що старі файли потребують перетворення;
- змінює спосіб інтерпретації даних, навіть якщо JSON синтаксично залишається валідним.

Додавання необов'язкового поля теж має бути контрольованим: у строгій схемі v1 невідомі поля відхиляються. Тому нове поле вимагає узгодження версії або чітко задокументованої політики сумісності.

### 10.3. Стратегія завантаження

Завантажувач має:

1. Перевірити маркер `format`.
2. Прочитати `schema_version`.
3. Вибрати валідатор/міграцію для відповідної версії.
4. Відхилити невідому версію з повідомленням про помилку.
5. Перетворити дані у внутрішню структуру Rust лише після успішного синтаксичного й семантичного контролю.

Майбутні старі версії можна мігрувати окремим інструментом Python. Не потрібно робити ядро складним універсальним конвертером усіх історичних форматів.

## 11. Валідація: Python і Rust

### 11.1. Python — зручний валідатор для розробника

Python-інструмент має давати ранні, зрозумілі повідомлення про помилки, перш ніж рівень запускається в грі. Мінімальний набір команд може бути таким:

```text
python tools/validate_level.py data/levels/prototype_01.json
```

Майбутні команди `convert_legacy.py`, `inspect_level.py` або `pack_assets.py` додаються окремо, коли виникне потреба. Їх не потрібно реалізовувати всі одночасно.

Валідатор перевіряє два рівні:

**Структурний рівень:** JSON має коректний синтаксис, потрібні ключі й правильні типи полів.

**Семантичний рівень:** ID унікальні, посилання існують, коди відомі реєстрам, правила сумісні, а дані не містять очевидних суперечностей.

Приклад очікуваного повідомлення:

```text
ERROR data/levels/prototype_01.json: objects[4].link_id = 99
      Посилання веде на відсутній об'єкт. Доступні ID: 1, 2, 3, 4, 5, 6.
```

Точний текст помилок може відрізнятися, але він має вказувати файл, шлях до поля, проблему та, коли можливо, спосіб її виправлення.

### 11.2. Rust — обов'язкова перевірка на межі runtime

Rust повторно перевіряє критичні умови. Не можна вважати, що дані безпечні лише тому, що їх колись перевірив Python: файли можуть бути змінені, пошкоджені або надані з іншого джерела.

Rust-завантажувач має відхиляти некоректну версію, дублікати ID, некоректні типи полів і недійсні посилання. Помилка завантаження повинна повертатися як визначений результат/помилка, а не приводити до частково ініціалізованого світу.

### 11.3. Чи потрібен окремий JSON Schema

Для автоматизованої структурної перевірки рекомендовано мати формальну JSON Schema, наприклад у `data/schemas/level-v1.schema.json`. У цьому документі нижче наведено її початковий варіант. Семантичні перевірки (унікальність ID та наявність цілі посилання) все одно виконуються додатковим кодом, тому що звичайної JSON Schema для них недостатньо.

## 12. Початкова JSON Schema

Це робочий варіант JSON Schema Draft 2020-12. Він формалізує структуру першого файлу, але **не встановлює значень числових реєстрів**, які ще треба звірити з реалізацією. Коли схема буде перевірена валідатором і кодом рушія, її можна винести в окремий `.json` файл.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.invalid/schemas/level-v1.schema.json",
  "title": "Modular Game Engine Level v1",
  "type": "object",
  "additionalProperties": false,
  "required": [
    "format",
    "schema_version",
    "level",
    "objects",
    "rules"
  ],
  "properties": {
    "format": {
      "const": "modular-game-engine-level"
    },
    "schema_version": {
      "const": 1
    },
    "level": {
      "type": "object",
      "additionalProperties": false,
      "required": ["id", "name"],
      "properties": {
        "id": {
          "type": "string",
          "pattern": "^[a-z0-9][a-z0-9_-]*$"
        },
        "name": {
          "type": "string",
          "minLength": 1
        },
        "description": {
          "type": "string"
        }
      }
    },
    "objects": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["id", "type_id", "state", "link_id", "access"],
        "properties": {
          "id": {
            "type": "integer",
            "minimum": 1
          },
          "type_id": {
            "type": "integer"
          },
          "state": {
            "type": "integer"
          },
          "link_id": {
            "oneOf": [
              { "type": "integer", "minimum": 1 },
              { "type": "null" }
            ]
          },
          "access": {
            "type": "integer"
          }
        }
      }
    },
    "rules": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": [
          "id",
          "source_type_id",
          "check_field_id",
          "check_value",
          "target_mode_id",
          "target_field_id",
          "action_id",
          "value"
        ],
        "properties": {
          "id": {
            "type": "string",
            "pattern": "^[a-z0-9][a-z0-9_-]*$"
          },
          "source_type_id": { "type": "integer" },
          "check_field_id": { "type": "integer" },
          "check_value": { "type": "integer" },
          "target_mode_id": { "type": "integer" },
          "target_field_id": { "type": "integer" },
          "action_id": { "type": "integer" },
          "value": { "type": "integer" }
        }
      }
    }
  }
}
```

Адрес `$id` з доменом `example.invalid` є навмисним заповнювачем документації, а не реально розміщеною схемою. Під час винесення схеми в репозиторій його слід замінити стабільним локальним URI або прибрати, якщо URI не потрібен.

## 13. Міграція з поточного текстового формату

Міграція має бути поступовою, з можливістю порівняти старий і новий результат.

### 13.1. Перетворення таблиці об'єктів

Для кожного рядка:

```text
object ID TYPE STATE LINK ACCESS
```

конвертер створює об'єкт:

```json
{
  "id": 1,
  "type_id": 1,
  "state": 0,
  "link_id": 2,
  "access": 1
}
```

Правила перетворення:

- префікс `object` стає типом запису і не зберігається як окреме поле JSON;
- `ID` → `id`;
- `TYPE` → `type_id`;
- `STATE` → `state`;
- `LINK` → `link_id`, причому `0` конвертується в `null`;
- `ACCESS` → `access`;
- порядок об'єктів зберігається.

### 13.2. Перетворення правил

Для кожного старого запису `event` конвертер читає числові поля у тому порядку, який визначено фактичним парсером і форматом файла. Перед написанням конвертера потрібно перевірити, чи поле `EVENT` є лише ключовим словом типу запису, і підтвердити точну кількість колонок за прикладами файлів.

JSON-ключі використовуються замість позиційного порядку, але значення кодів переносяться без переосмислення. Конвертер не повинен самостійно перейменовувати коди на `terminal`, `door`, `set_state` тощо, доки ці відповідності не підтверджені кодом і не внесені до реєстрів.

Для діагностики можна створити стабільні ID правил, наприклад `legacy_rule_0001`, `legacy_rule_0002` тощо. Ці ID мають відображати порядок старих записів і не змінювати його. Вони є метаданими конвертації, якщо runtime-структура не підтримує окремий ID.

### 13.3. Перевірка еквівалентності

Перед заміною старого формату потрібно виконати контрольний тест:

1. Завантажити рівень старим завантажувачем.
2. Завантажити його JSON-версію новим шляхом.
3. Порівняти кількість об'єктів, їхні ID, типи, стани, зв'язки й значення `access`.
4. Порівняти кількість і порядок правил та всі числові поля кожного правила.
5. Виконати однакову послідовність тестових подій і порівняти кінцевий стан світу.
6. Переконатися, що різниця є нульовою або пояснюється явною, документованою зміною поведінки.

Старі файли не видаляються відразу після першої успішної конвертації. Вони залишаються тестовим еталоном до завершення міграції.

## 15. Вимоги до завантажувача Rust

Завантажувач у Rust має виконувати чітку послідовність:

1. Відкрити визначений файл даних і обробити помилку читання.
2. Розібрати JSON у типізоване представлення.
3. Перевірити маркер `format` і підтримуваний `schema_version`.
4. Перевірити унікальність ID та коректність посилань між об'єктами.
5. Перевірити числові коди за реєстрами, коли вони будуть визначені.
6. Побудувати внутрішні структури світу.
7. Опублікувати новий світ лише після успішної повної побудови.

Неприпустимо залишати активний світ у напівзавантаженому стані після помилки. Якщо рівень завантажується під час гри, слід спочатку побудувати й перевірити нове представлення окремо, а потім атомарно замінити активний стан відповідно до правил архітектури.

Rust не повинен покладатися на Python для кожного запуску гри. У мобільній збірці потрібні дані повинні завантажуватися Rust-ядром без запуску скрипта підготовки.

## 16. Підготовка й пакування

На першому етапі JSON може бути і авторським, і runtime-форматом. Не слід завчасно створювати власний бінарний контейнер лише заради швидкості.

Якщо профілювання згодом покаже, що читання JSON або розмір текстових файлів є значущою проблемою, можна додати етап пакування:

```text
JSON source files
       │
       ▼
Python validation / build tool
       │
       ▼
optional packed runtime data
       │
       ▼
Rust loader
```

Вихідні JSON-файли при цьому залишаються зручним джерелом для розробника. Пакований формат вважатиметься згенерованим артефактом, а не ручним джерелом істини. Його специфікація з'явиться окремо, лише якщо це буде обґрунтовано вимірюваннями або вимогами захисту ресурсів.

## 17. Поширені помилки й визначена реакція

| Проблема | Реакція валідатора |
|---|---|
| Некоректний JSON | Помилка з файлом і позицією парсера |
| Немає `schema_version` | Відхилити файл; не вгадувати версію |
| Невідома версія | Відхилити або спрямувати в окрему міграцію |
| Повторюється ID об'єкта | Помилка із зазначенням ID і всіх позицій |
| `link_id` посилається на відсутній об'єкт | Помилка цілісності |
| Невідоме поле | Помилка у строгій схемі v1 |
| Неправильний тип даних | Помилка із шляхом, очікуваним і фактичним типом |
| Код реєстру невідомий | Помилка після того, як відповідний реєстр визначений; до того — явне попередження інструмента розробки |
| Порядок правил змінився після конвертації | Помилка тесту еквівалентності |
| Дія правила несумісна з цільовим полем | Помилка семантичного валідатора після документування реєстрів |

Усі помилки мають приводити до контрольованої відмови завантаження, а не до мовчазного пропуску невідомих полів чи заміни значень на нулі.

## 18. Відкладені питання

Наступні пункти не слід вважати вже вирішеними:

1. **Повний словник типів об'єктів.** Потрібно підтвердити, що саме означають `TYPE = 1`, `2`, `3`, `4` у поточному прототипі.
2. **Словник полів правил.** Треба звірити значення `CHECK_FIELD` і `TARGET_FIELD` з усіма гілками `rules.S`.
3. **Словник режимів цілі.** Треба зафіксувати значення `TARGET_MODE` та обробку кожного режиму.
4. **Словник дій.** Треба встановити всі допустимі значення `ACTION`, їхні параметри й поля, які вони можуть змінювати.
5. **Семантика `SOURCE_TYPE`.** Потрібно підтвердити, чи це тип об'єкта-джерела, фільтр події або інший критерій.
6. **Семантика `ACCESS`.** Потрібно документувати, чи це прапорець, маска, рівень доступу або інше значення.
7. **Дозволені стани.** Можливо, стани залежать від типу об'єкта; після підтвердження їх можна додати до реєстрів або правил валідації.
8. **Зовнішні ресурси.** Шляхи до текстур, звуків і шейдерів потрібно описати окремо, коли система ресурсів буде визначена.
9. **Локалізація.** Текст інтерфейсу й діалогів бажано зберігати окремо від логічних об'єктів рівня.
10. **Збереження гри.** Save-файл повинен мати власну версію формату і не змішуватися з вихідним описом рівня.

## 19. План реалізації

### Етап A — інвентаризація поточного формату

- Зібрати приклади реальних файлів об'єктів і правил.
- Звірити парсер C та офсети/поля, які читаються в `world.S`, `events.S`, `rules.S` і пов'язаних модулях.
- Зафіксувати фактичне значення кожного числового коду.
- Перевірити значення `0` у кожному полі окремо; не переносити правило `LINK = 0` автоматично на інші поля.

**Критерій завершення:** структура старого формату задокументована без припущень.

### Етап B — JSON-файл еталонного рівня

- Створити `data/levels/prototype_01.json` за прикладом у цьому документі.
- Зберегти порядок та числові значення з поточного еталонного рівня.
- Звірити об'єкти построчно зі старим текстовим файлом.
- Не переписувати правила, поки їхню повну форму не буде підтверджено.

**Критерій завершення:** JSON-опис об'єктів відповідає старій таблиці.

### Етап C — Python-валідатор

- Додати перевірку JSON-синтаксису й схеми.
- Додати перевірку унікальності ID і посилань.
- Після інвентаризації додати реєстри кодів.
- Додати перевірки для правил.
- Створити негативні тести: дублікат ID, відсутнє посилання, невідома версія, неправильний тип.

**Критерій завершення:** валідатор детерміновано приймає коректний рівень і зрозуміло відхиляє некоректний.

### Етап D — конвертер старого формату

- Реалізувати читання поточних файлів.
- Перетворити їх у JSON без зміни числових значень.
- Після кожної конвертації запускати валідацію.
- Додати тест, який порівнює результат конвертації з еталонними даними.

**Критерій завершення:** повторна конвертація того самого файла дає еквівалентний результат і не змінює порядок правил.

### Етап E — Rust-завантажувач

- Описати Rust-структури для JSON v1.
- Додати парсинг, версіонування та семантичну перевірку.
- Перетворити JSON у внутрішню модель світу.
- Перевірити поведінкову еквівалентність зі старим завантажувачем.

**Критерій завершення:** еталонний рівень завантажується Rust-ядром, а тестові сценарії дають ті самі результати, що й старий прототип.

## 20. Критерії готовності формату v1

Формат можна вважати готовим до першої стабільної реалізації, коли:

- [ ] структура JSON v1 зафіксована й перевіряється формально;
- [ ] числові коди об'єктів, полів, режимів та дій звірені з кодом;
- [ ] конвертація не змінює ідентифікатори, значення або порядок правил;
- [ ] Python-валідатор виявляє структурні й семантичні помилки;
- [ ] Rust повторно перевіряє критичні умови;
- [ ] є тест еквівалентності для старого та JSON-завантажувача;
- [ ] невідома версія схеми приводить до явної помилки;
- [ ] джерельні JSON-файли не залежать від запуску Python під час гри.

## 21. Підсумкове рішення

Для першої реалізації рушія затверджується такий підхід:

- **JSON** — основний читабельний формат ігрових даних.
- **Python** — інструмент перевірки, конвертації та підготовки.
- **Rust** — runtime-завантажувач і єдиний власник активного стану світу.
- **ARM64 Assembly** — працює з визначеними структурами й числовими кодами, але не читає JSON і не виконує загальну маршрутизацію між мовами.
- **Kotlin** — звертається до ядра через API і не дублює модель світу.
- **YAML** — не використовується на першому етапі; його можна додати пізніше як додатковий авторський формат, якщо це доведе практичну користь.
- **Бінарне пакування** — відкладене до появи підтвердженої потреби.

Перший практичний крок — інвентаризація наявних полів та числових кодів, а не негайне переписування ігрової логіки. JSON має точно описати те, що вже працює, після чого можна безпечно змінювати внутрішню реалізацію рушія.
